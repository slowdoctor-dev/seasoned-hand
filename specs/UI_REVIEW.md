### F1 (H) — Three-panel `Group` collapsed to 277 px content height

**Status**: FIXED at iter-2

**Threat model**: `react-resizable-panels` v4 applies an inline
`height: 100%` to the `Group` div. Body was `min-h-full flex flex-col`,
so the parent's height was **indefinite** (a `min-height` constraint
without a definite `height`). Per CSS spec, percentages on a flex item
against an indefinite parent collapse to auto/content size — so the
Group rendered at exactly 277 px (the natural height of its children's
content) instead of filling the 900 px viewport. Below ~280 px the
viewport was just empty white.

**Root cause discovery**: `browser_evaluate` reported
`rootInlineStyle: "height:100%;..."` and `bodyMinHeight: 100%` —
indefinite parent + percentage child = collapse.

**Fix**: body className `min-h-full flex flex-col` → `h-full`. Body now
has a definite height (`height: 100%` of html which is `h-full`), so
Group's inline `height: 100%` resolves to 900 px. Comment in `layout.tsx`
documents the constraint so a future "let's simplify body to just `flex`"
edit doesn't regress.

### F3 (M) — Right-panel tab strip overflowed outside the panel

**Status**: FIXED at iter-3 + iter-3b

**Threat model**: `AgentComputer` renders 7 tabs (`Browser`, `Terminal`,
`Editor`, `Verifier`, `Deliverables`, `Decisions`, `Files`) in a
narrow ~430 px panel. Each button was `flex-1` (equal share with
`flex-basis: 0`) but flex children won't shrink below their min-content
width — and "Deliverables" alone is ~90 px. The buttons' total min-content
was 502 px, so the nav stretched 502 px wide inside a 430 px-wide
parent. The overflow bled out and produced a horizontal scrollbar at
the BOTTOM of the entire right panel (the closest scroll ancestor was
the body, not the panel).

**Fix (iter-3)**: change nav to `flex flex-none overflow-x-auto
whitespace-nowrap border-b`, buttons to `flex-none` (natural width).
The nav itself becomes the scroll container; the rest of the panel
stays put.

**Fix (iter-3b)**: add `[scrollbar-width:none]
[&::-webkit-scrollbar]:hidden` to the nav so the scroll-affordance
chrome doesn't clutter the strip. Mouse-wheel scrolling and touch still
work; users who want to see all tabs can drag the panel divider wider.

### F4 (M) — Project list rendered "Failed to fetch" + "Loading…" simultaneously

**Status**: FIXED at iter-4

**Threat model**: `<ProjectList>` initialized `projects = null` and
`error = null`. The fetch's `.catch()` set `error` but left `projects`
at `null`, so the render condition `projects === null && <Loading>`
still matched alongside the now-truthy `<ErrorBanner>`. The result was
a confusing stack: a red "Failed to fetch" immediately above a grey
"Loading…" row — the user couldn't tell whether the request was still
in flight or had failed.

**Fix**: `.catch()` now also calls `setProjects([])`. The empty array
suppresses the Loading row; the synthetic `Archive (legacy)` entry
below the project list is hardcoded so it still appears.

### F5 (L) — Desktop-centric "on the left" copy across 5 empty-state messages

**Status**: FIXED at iter-4 (same commit as F4)

**Threat model**: 5 components shipped strings like *"Select a task on
the left to view its browser."* The mobile view collapses the
three-panel layout into a tab bar, so "on the left" describes nothing
mobile users can act on — they see the message inside the same tab
they'd need to act FROM.

Affected:
- `task-list.tsx` — *"Select a project on the left to see its tasks."*
- `agent-computer/browser-tab.tsx` — *"Select a task on the left..."*
- `agent-computer/editor-tab.tsx` — *"Select a task on the left..."*
- `agent-computer/deliverables-tab.tsx` — *"Pick a task on the left..."*
- `agent-computer/terminal-tab.tsx` — *"Select a task on the left..."*

**Fix**: dropped "on the left" — *"Select a task to view its browser."*
etc. Neutral phrasing works on both layouts.

### Things deliberately not changed

- **Right-panel tab clipping at narrow widths** — at the default 30%
  share (~430 px on a 1440-wide viewport) the last tab ("Files") is
  outside the visible region. Users can drag the panel divider wider
  or scroll the nav. Real fix would be design work (shorter labels or
  icons) — out of scope for hardening.
- **Center panel empty area** — no first-run illustration / onboarding
  hint. Feature scope, not hardening.
- **Next.js dev-tools "N" floating badge** — visible in dev mode only,
  doesn't ship to production. Phase 5+ deployments use `next start`
  which suppresses it.

### Lessons (for the next UI hardening cycle)

- Next.js Turbopack 16.2 watching files on `/mnt/c` (WSL Windows
  filesystem) does NOT pick up changes reliably even with
  `CHOKIDAR_USEPOLLING=1` / `WATCHPACK_POLLING=true`. **Every edit
  required a dev-server restart** to take effect. The verification
  loop saturated faster once I batched edits per restart.
- Playwright `browser_evaluate` is faster than visual inspection for
  layout debugging — `getBoundingClientRect` + `getComputedStyle` pin
  the root cause of layout collapse in seconds where staring at a
  screenshot would not.
- The `react-resizable-panels` v4 + `min-height` + flex column gotcha
  (indefinite-height parent collapses percentage child) is a
  surprisingly common Next.js layout bug — worth documenting in the
  layout file's comment block, which iter-2 did.
